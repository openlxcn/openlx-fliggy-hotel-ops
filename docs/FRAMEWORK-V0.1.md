## 一、产品目标与定位

核心目标：帮助酒店、宾馆、客栈和民宿增加飞猪真实有效订单与实际履约房晚，改善可核验的搜索可见性、曝光和转化表现，同时守住酒店结算收入、订单贡献及履约底线。

目标用户：酒店与民宿老板、店长、运营人员及获得授权的运营服务团队。

建议定位：

> 一名能识别酒店实际经营模式，持续管理日历房、价格计划、套餐预约与店铺转化，并在授权范围落实动作、复盘结果的飞猪AI运营助手。

不是只做报告，不是只会自动降价，不是消费者代订旅行助手，也不是用虚假订单和评价影响排名的工具。

## 二、继承的产品底线

继续采用“总控Skill＋Chrome浏览器执行器＋数据层＋OTA运营知识库＋收益管理引擎＋HTML报告系统”。

保留12大优势；免费版提供完整体检、内容充分的HTML报告、真实好评的商家自动回复以及差评建议和确认发布；标准版必须有基础规则自动调价，不能只去水印；付费报告去除OpenLX与法匠科技的推广署名；至尊版提供平台适配的获客优化与有限人工定制。

独立安装、独立升级、独立文档和授权，不强制安装携程助手、美团助手或AG1—AG6。可复用已验证的底层组件，但飞猪的页面、身份、价格、交易和规则必须独立适配。

## 三、公开核验所支持的边界

1. 飞猪官方帮助中心明确列出酒店eBooking入口；官方商家App说明涵盖订单、价格、房态、评价和图片管理。[S1][S2] App存在某项能力，不代表每个商户的网页都暴露同等接口。
2. 飞猪官方公开介绍了免费酒店商家AI助理，覆盖操作、订单账务查询和经营建议。[S3] 本产品不能以“官方没有AI/只会建议”为商业卖点。应以酒店自定策略、交易模式识别、履约管理、可带走的报告与持续复盘差异化，优先利用已有可靠原生能力。
3. 官方帮助文档区分供货底价、售价及不同经营模式。[S4] 文档含历史说明，程序必须以商户当前合同与实际字段核对，不将历史例子硬编码为所有账号通用规则。
4. 酒店API目录列有价格计划、房价、库存、酒店/房型和部分评价相关能力；具体API存在授权条件，也存在废弃接口。[S5][S6][S7][S8] 文档可见、标注免费，不代表任意应用自动获得权限。
5. FlyAI公开介绍的是旅行搜索、商品与动态库存、旅行交易等开放能力。[S9] 搜索/预订授权不能推导为修改酒店后台的经营授权。
6. 官方实价有房帮助说明涉及日历、套餐、预约及多种付款订单。[S10] 应保存当前商户适用规则来源和核验时间，不将飞猪国际或其他业务类目规则直接套用到境内酒店。

## 四、先识别经营身份，再决定执行方式

### 4.1 建议覆盖顺序

核心主线：境内酒店、客栈、民宿可操作的酒店eBooking业务。

能力扩展：经授权的旗舰店/专营店、酒店套餐、会员活动及其他商家中心入口。有真实入口、资质与权限则接入；缺失只暂停该项，不让整套基础助手停止工作。

不默认首期同时承包国际酒店、机票、旅行社线路、全集团旗舰店或所有阿里生态平台。

### 4.2 必须分别登记的对象

| 对象 | 含义与要求 |
|---|---|
| 实体酒店 | 实际经营的物业；绑定名称、地址及酒店标识，防止同名酒店误匹配。 |
| 授权主体/账号 | 谁拥有本次操作权限，覆盖哪家酒店、哪些角色。 |
| 店铺/销售主体 | 当前可管理的自有店铺、平台经营入口或销售渠道；不能把其他卖家的报价当成本账号可改字段。 |
| 房型与价格计划 | 房型、早餐、退改、会员资格、渠道、入住条件和价格计划分别映射。 |
| 商品预约方式 | 指定日期的日历房、先购买后预约的套餐等，保存实际商品类型。 |
| 付款与结算方式 | 预付、到店付、信用住或当前实际支持的方式。此维度与商品预约方式分开，不强行设计为互斥产品列表。 |
| 库存与价格主控 | PMS、渠道管理器、集团系统、平台工具或助手，明确同一字段谁负责写入。 |

一个主体管理多家酒店，不代表一份单店授权能修改全部门店。

## 六、飞猪专属重点：必须落到业务动作

### 6.1 供货底价与客人销售价分开

至少保存：价格类型、价格计划、原价、新价、优惠承担方、预估/实际结算、履约变动成本、可操作权限和依据。

产品中的“最低允许价”命名为“酒店收益底线/最低供货价/最低零售价”等清楚字段，避免与平台“底价模式”混淆。

示意：后台可改的是280元供货价，客人端看到的是360元零售价。助手不能因为用户说“零售价上调20元”就直接把供货价改到300元并宣称目标已实现。应判断是否有零售价权限，或提出供货策略并核验客人端观察值。

调价目标以正确价格类型计算，不能用零售价假装酒店收入，也不能把已在净结算中扣掉的费用再次扣除。

### 6.2 价格计划不能互相覆盖

含早餐、不同退改政策、会员/非会员及特定日期策略分别识别。修改目标必须锁定酒店、房型、价格计划、适用日期及条件。

官方文档区分全量与增量更新。[S6][S7] 开发时核验真实语义，不能为了修改一个日期错误覆盖其他日期；出现原生工具或PMS已更新时，重新计算而非用旧提案覆盖。

### 6.3 套餐售出不等于已经有入住日期

独立记录：售出份额、每份权益、已退款权益、已预约房晚、未预约权益、有效期、不适用日期、加价条款和可承接能力。

示意（暂不考虑退款）：售出100份两晚套餐，其中40份已预约，意味着80个已预约房晚，另有120个尚未分配到日期的权益房晚。不是“今天卖出100间房”，也不是“未预约就没有履约责任”。

价格和库存策略要看到套餐的后续预约压力。不得凭历史未核销比例默认无限售券；不得事后随意缩减已售商品承诺；平台允许且用户认可的预约提醒可以辅助转化，但不是无差别营销群发。

### 6.4 会员与信用住分别管理

会员价/会员权益属于资格与产品策略；信用住属于实际开通的交易、履约及结算流程。不能用“支付状态不是已付款”这一普通预付判断，误判有效信用订单。

记录实际权益，例如早餐、升房和延迟退房，计算成本与兑现条件；并核对入住、离店、扣款/结算等必要操作。不开通即不强行标注，不默认替商家加入会员互通、信用住或任何收费计划。

资金扣款、退款、赔偿及无法可靠逆转的状态变化，需要对应的明确授权和真实业务依据。不要把“核验成功”误当成“资金已到账”。

### 6.5 素材文件夹用于真实成交表达

建议流程：读取指定素材 → 去重分类 → 对应酒店/房型/权益 → 生成主图与详情改进建议 → 确认或范围授权更新 → 记录版本 → 复查表现。

优先产出：房型图文、酒店详情、套餐说明、交通停车与设施FAQ、活动商品素材。短视频、直播或内容社区，仅在账号当前支持且有权限时接入，不承诺全账号每日自动发布游记。

保持真实场景和品牌一致性，不生成酒店没有的设施，不把无授权客人照片直接上传；每日巡检不等于每天强制改名换图。

### 6.6 AI搜索可理解性作为可选增强

FlyAI的公开说明强调官方商品库和动态库存。[S9] 因此可以提出“资料可理解性与实时可售性”诊断：真实地理位置、床型、早餐、宠物、适用人数、退改、连住等字段清晰且一致。

这是产品设计推论，不是已证实的排名因子。是否被推荐必须用允许范围内的固定场景观察验证；不得承诺修改某字段必获AI推荐，也不声称知道千问或飞猪的内部权重。

FlyAI可作为获授权的辅助查询，不强制安装，不替代商家经营权限。不要暗中植入推广返佣链接、改变商家销售归属或在订阅之外增加未披露分成。

## 七、围绕真实订单增长安排日常工作

主链：连接并识别账号 → 读取数据与当前规则 → 诊断主要问题 → 选择少量优先动作 → 授权执行 → 回读 → 复查经营结果。

| 经营症状 | 优先检查与动作 |
|---|---|
| 查询不到/无可售报价 | 先检查酒店匹配、店铺权限、营业/商品状态、日期库存、价格计划条件，再讨论降价。 |
| 有曝光点击低 | 核对主图、真实卖点、条件可比价格和展示准确性。 |
| 有访问下单少 | 检查权益、取消与预约限制、产品差异和咨询问题。 |
| 套餐卖出多预约少 | 区分尚未到预约期和真正预约障碍；核对可约日期、说明、提醒与承接能力。 |
| 有订单结算低 | 分析供货/零售价、优惠承担、佣金、权益及变动成本。 |
| 订单响应或履约异常 | 优先处理原生提醒、待确认和真实接待；不等待竞品扫描周期。 |
| 节假日临近且预订进度良好 | 评估提价、持价、减少补贴、保留库存和套餐承接，而不是机械降价。 |

可选目标：增单优先、收益优先、稳健运营；都不能突破真实库存、价格与费用底线。

## 八、指标和排名口径

核心看：有效预订间夜、实际履约间夜、商家结算/订单贡献。售出套餐份额、待预约权益和已预约房晚单列。

信用住等交易方式不能被“仅统计已付款订单”的通用口径排除。取消、退款、部分退改按订单行和权益更新；不要用券销量替代实际入住。

自然搜索位置、广告位置、店铺/商品表现与内部诊断分分开。观察必须保存查询词、日期、人数、城市/定位、排序筛选、账号状态、采样时刻和深度。前N未见只报告前N未见，不编造绝对排名。

以已有数据建立基线；没有历史也先修复已证实问题。建议7/14/28天复查，考虑星期、节日、价格、库存、活动和广告变化。前后对比不自动等于因果，不保证订单增幅、满房或排名第一。

只持有飞猪渠道数据时，不伪装为全店入住率、ADR和RevPAR。平台曝光/访问分母不兼容时不拼凑转化率。

### 免费版

完整体检、充分HTML报告、真实好评自动商家回复、差评建议及确认发布、基础信息/图片/价格/库存/订单/套餐风险诊断，建议保留5家手动竞品快照及确认后的基础操作。

免费版不是只出问题不给答案；有权限和技术条件的自动回复必须真实执行，不把文案生成当完成。

### 标准版

建议10家竞品、未来30天重点日期、每日两轮价格观察；加入基础规则自动调价、异常提醒、价格计划与活动成本分析、日报周报、历史对比及去推广署名报告。订单与点评调度独立，不沿用价格扫描频率。

### 至尊版

建议20家竞品、未来90天重点日期、每日四轮价格观察；加入多因素收益策略、适用账号的套餐预约与权益分析、供货/零售差异诊断、素材与店铺成交优化、已开通会员/信用住专项分析、专题报告和人工定制。

没有旗舰店的用户仍应获得适合自己eBooking业务的高级运营与收益服务；购买软件不能自动获得平台经营权限。

### 人工服务与包年权益

建议至尊版单店首次一次30分钟远程协助、一张定制策略卡及一次文字校正；首12个月不因月度或季度续费重复重置，软件缺陷工单不占用权益。

至尊包年建议每付费年度一次“酒店卖点与套餐成交表达蒸馏”：定位、客群、真实卖点、语言风格、价格计划/套餐建议、30天动作及可导入配置。同一酒店此前确认的事实经授权复用，避免重复采访。

月费/年费不默认含广告费、无上限模型调用、云端全天托管和无限人工代运营。基础功能应有规则或模板兜底；模型和外部数据费用购买前披露。电脑关机/休眠时本地任务暂停，不承诺永久在线。

## 十、浏览器、接口与执行方式

Chrome仍是可见、可接管的工作入口。每个授权身份使用独立Profile，不直接复用日常Chrome默认目录，不导出会话给第三方或公开仓库；登录失效要求人工验证，不绕过验证码。

优先级是能力逐项选择：已有授权且稳定的官方经营API → 实際允许的官方后台浏览器操作 → 数据导入或精确人工协助。这里的箭头不是强迫所有商户先申请API，浏览器基础主线不得因此停止。

建议复用现有轻量执行器、数据存储与报告模板，不为单平台新造多层代理审批。普通操作采用一次范围授权；涉及新支出、真实事实缺口或不可逆承诺只确认相关动作。
